# Personal Flight Log

**사이트**: https://ga3ulkim.github.io/flight-log-manual/

비행을 직접 기록하고 지도, 통계, 타임라인, `PLAY MY JOURNEY`로 다시 보는 개인용 비행 아카이브입니다. 사이트를 열면 항상 전용 기록 관리 화면에서 시작하며, 여러 비행을 연속으로 추가·수정·삭제한 뒤 `내 비행 기록 보기`를 눌러 전체 아카이브로 이동합니다.

```text
direct flight entry
→ current page memory
→ map / statistics / rankings / timeline / journey replay
```

## 주요 기능

- 비행 추가, 수정, 단건 즉시 삭제
- 여러 비행을 연속 입력하는 기록 화면과 명시적인 전체 아카이브 전환
- 선택적인 출발 공항 현지 시각과 시간대·날짜 변경을 반영한 예상 도착 표시
- IATA·영문 공항명·도시·국가와 검토된 한국어 별칭으로 찾는 로컬 공항 자동완성
- 영문 이름·IATA·ICAO로 찾는 현재 및 2000년 이후 역사적 항공사 로컬 자동완성
- 현재 데이터베이스에 없는 역사적 공항의 직접 입력과 선택적 좌표 입력
- 국가 코드에 따른 국내선/국제선 자동 구분
- 연도·국내선·국제선 필터와 비행 편수, 거리, 국가, 공항 통계
- 사용자 정의 SVG 세계 지도, 노선 상세, 팬·휠·핀치 확대, 세계 경도 래핑
- 국가·도시·공항·운항사 순위와 최신순 Flight Timeline
- 기종별 실루엣, 카메라 추적, 버스·페리 환승을 포함한 시간순 여정 재생
- 버전이 있는 JSON 백업·복원(병합 또는 교체)과 한국어 CSV 내보내기
- 기존 CSV/XLS/XLSX 기록의 선택적 1회 마이그레이션
- 360px 모바일부터 넓은 데스크톱까지 대응

## 세션 기록과 개인정보

비행 기록은 **현재 페이지가 열려 있는 동안의 메모리**에만 유지됩니다. 새로고침하거나 페이지를 닫았다 다시 열거나 새 탭을 열면 빈 기록 화면에서 다시 시작합니다. 계정, 로그인, 애플리케이션 백엔드, 서버 데이터베이스, 비행 기록 업로드 API는 없습니다. 추가·수정·삭제와 공항·항공사 검색은 브라우저 안에서 처리됩니다.

기록을 다음 방문에도 보존하려면 페이지를 떠나기 전에 `데이터 관리`에서 JSON 백업이나 CSV 내보내기를 사용하세요. JSON 복원과 기존 CSV/XLS/XLSX 가져오기도 현재 페이지 세션만 채우며, 가져온 뒤 새로고침하면 다시 초기화됩니다. 자동 저장이나 기기 간 동기화는 없습니다.

이전 개발 버전이 만들었던 `personal-flight-log-manual` IndexedDB는 V1.3에서 열거나 읽거나 자동 삭제하지 않습니다. 과거 데이터가 화면에 다시 나타나지 않으며, 시작 동작도 해당 데이터베이스의 삭제 성공 여부에 의존하지 않습니다. 필요하면 브라우저의 사이트 데이터 관리 기능으로 직접 정리할 수 있습니다.

개인 백업과 CSV 내보내기 파일은 Git에 추가하거나 프로젝트의 `src`/`dist` 안에 두지 마세요. 이 저장소는 루트의 비행 CSV·Excel 파일, 로컬 참조 파일, `flight-log-backup-YYYY-MM-DD.json` 파일을 무시하고 개발/미리보기 서버에서도 직접 제공하지 않도록 막습니다.

## 화면 이동 정책

- 사이트 시작·새로고침·재방문·새 탭은 항상 기록 0개인 기록 관리 화면에서 시작합니다.
- 같은 페이지 안에서 기록 관리 화면과 전체 아카이브를 오가는 동안에는 현재 세션 기록이 유지됩니다.
- 저장 후에도 자동으로 지도·통계 화면으로 이동하지 않습니다.
- 한 편 이상 저장하면 `내 비행 기록 보기`가 나타납니다.
- 전체 아카이브는 `내 비행 기록 보기`를 누를 때만 열리며, 마지막 화면을 별도 환경설정으로 저장하지 않습니다.
- 전체 아카이브의 `기록 관리`로 기록 화면에 돌아갈 수 있고, `+ 비행 추가`는 기존처럼 현재 화면에서 바로 추가 대화상자를 엽니다.
- 기록 화면의 개별 `삭제`는 한 번의 클릭으로 현재 세션에서 즉시 삭제됩니다. `데이터 관리`의 `모든 비행 기록 삭제`와 JSON 교체 확인은 기존 보호 절차를 유지합니다.

## 백업, 복원, 이동

`데이터 관리`에서 다음 작업을 할 수 있습니다.

- **JSON 백업**: 안정된 ID, 날짜, 선택적 출발 시각, 입력 내용, 공항 이름·도시·국가·좌표·IANA 시간대와 선택한 항공사 이름·코드·국가 스냅샷을 저장합니다.
- **JSON 복원**: 내용을 먼저 검증한 뒤 현재 세션 기록과 병합하거나 전체 교체합니다. 병합 시 같은 ID는 `updatedAt`이 더 새로운 기록만 반영됩니다. 새로고침하면 복원 기록도 사라집니다.
- **CSV 내보내기**: UTF-8 BOM이 포함된 한국어 CSV를 만들며, 시각이 있으면 `YYYY.MM.DD HH:mm`, 없으면 날짜만 내보냅니다. 기존 수식 중립화와 Flight Log 파서 호환성을 유지합니다.
- **기존 CSV / Excel 가져오기**: 파일을 로컬에서만 읽고 확인 후 현재 세션에 추가합니다. 가져온 기록도 새로고침하면 사라집니다.
- **모든 기록 삭제**: 강한 확인을 거친 뒤 현재 세션의 비행 기록을 비웁니다.

## 기록 스키마

각 기록은 변경되지 않는 문자열 ID와 `createdAt`/`updatedAt`, 스키마 버전을 가집니다. 날짜는 시간대 변환이 없는 `YYYY-MM-DD` 날짜 전용 값이며, 선택적인 `departureTime`은 출발 공항의 현지 벽시계 `HH:mm` 값입니다. 브라우저 시간대나 JavaScript `Date`를 원본 입력으로 저장하지 않습니다. 출발·도착 공항은 IATA, 공항명, 도시, ISO 국가 코드, 표시 국가명, 위도·경도와 IANA 시간대를 저장 당시 스냅샷으로 보존합니다. 목록에서 선택한 항공사는 영문 canonical 이름, 선택과 일치하는 IATA·ICAO 코드와 선택적 국가를 함께 스냅샷합니다. 여러 코드를 가진 항공사는 검색한 코드가 명확할 때 그 코드를 보존하며, 동명 항공사는 코드·국가로 다시 식별합니다. 직접 입력한 항공사에는 메타데이터를 만들지 않습니다. 이후 공개 데이터가 갱신되어도 기존 기록을 자동으로 다시 쓰지 않습니다.

V1.4의 새 JSON 백업은 백업/비행 스키마 V2로 내보냅니다. V1 백업은 계속 받아 메모리에서 V2로 검증하며, 없던 출발 시각·시간대·항공사 메타데이터를 임의로 채우지 않습니다.

현재 공항 목록에 없는 공항도 저장할 수 있습니다. 좌표가 없으면 기록·통계·타임라인에는 남고 지도 거리와 재생 기하에서만 제외됩니다. 국가 코드를 알 수 없는 직접 입력 공항은 통계를 임의로 만들지 않도록 국내선 또는 국제선을 사용자가 선택해야 합니다.

## 공항 데이터

좌표와 검색 메타데이터는 [OurAirports public-domain data](https://ourairports.com/data/)에서 한 번에 생성합니다. 각 좌표의 IANA 시간대는 유지보수 시점에만 MIT 라이선스의 [geo-tz](https://github.com/evansiroky/node-geo-tz) comprehensive 경계 데이터로 계산합니다. 그 경계는 [timezone-boundary-builder](https://github.com/evansiroky/timezone-boundary-builder)의 IANA 정렬 산출물이며, 생성 코드에는 MIT, 경계 산출물에는 ODbL이 적용됩니다.

- 작은 좌표 인덱스는 지도와 분석에서 즉시 사용합니다.
- 공항명·도시·국가가 포함된 검색 인덱스는 추가/수정 화면을 열 때만 지연 로드합니다.
- 브라우저에는 공항별 시간대 ID 한 개만 포함하며 원시 시간대 GeoJSON/polygon은 배포하지 않습니다.
- 사용자 입력 중 외부 공항 API를 호출하지 않으며 원본 CSV를 배포하지 않습니다.
- `Intl.DisplayNames`가 있으면 ISO 국가 코드를 한국어 국가명으로 표시하고, 없으면 코드로 대체합니다.

한국어 검색은 생성된 OurAirports 값을 번역하거나 덮어쓰지 않고, 별도로 검토한 작은 로컬 별칭 overlay를 검색 키로 더합니다. 현재는 대한민국 주요 여객 공항과 회귀 테스트에 쓰는 주요 국제 허브를 우선하며 모든 공항의 한국어 이름을 제공한다고 주장하지 않습니다. 예를 들어 `인천`, `서울`, `김포`, `부산`, `김해`, `제주`, `로스앤젤레스`, `도쿄`, `오사카`를 검색할 수 있습니다. 이 파일은 생성 데이터와 분리되어 월간 OurAirports 갱신에 덮어써지지 않으며, 입력 중 외부 번역·지오코딩 요청을 보내지 않습니다.

## 예상 비행 시간과 현지 도착

출발 시각을 입력하고 양쪽 공항의 시간대를 알 수 있을 때 `PLAY MY JOURNEY`의 항공편 카드에 출발 현지 시각, **예상 도착** 현지 시각, **예상 비행시간**을 표시합니다. 이는 실제 운항 스케줄이 아닙니다. 고정 35분과 대권 거리 기준 850km/h를 합산해 5분 단위로 반올림하고 최소 45분을 적용하는 하나의 단순한 block-time 모델이며, 바람·기상·ATC·실제 항로·항공사 여유 시간을 모델링하지 않습니다. 재생 애니메이션 속도와 카메라 동작에는 영향을 주지 않습니다.

현지 출발 날짜·시각은 IANA 시간대에서 해석한 뒤 절대 시각에 예상 시간을 더하고 도착 공항 시간대로 변환합니다. DST 순방향 전환으로 존재하지 않는 출발 시각은 저장 전에 오류로 안내하고, 반복되는 가을 시각은 앞선 instant를 일관되게 선택합니다. 시간이나 시간대가 없으면 기록과 재생은 그대로 동작하되 도착 시각을 추측하지 않습니다. 지상·해상 환승 카드에는 항공편 시각을 표시하지 않습니다.

같은 날짜의 재생 순서는 시각이 있는 항공편을 `HH:mm` 오름차순으로 놓고 시각이 없는 항공편을 그 뒤에 둡니다. 같은 시각 또는 시각 없음끼리는 기존 생성 순서/안정 ID 기준을 사용합니다. Timeline은 같은 규칙을 최신순 표현에 맞게 뒤집되, 시각 없는 기록은 해당 날짜의 시각 있는 기록 뒤에 유지합니다.

## 항공사 데이터

항공사 자동완성은 [Wikidata Query Service](https://query.wikidata.org/)의 CC0 구조화 데이터를 유지보수 시점에 정제한 로컬 지연 로드 인덱스입니다. 현재 생성본은 4,702개 항공사를 포함합니다. 영문 label을 우선하고, 영문 label이 없을 때만 Latin 문자가 있는 Wikidata의 언어 독립 `mul` label을 canonical 표시 이름으로 사용합니다. 검색에는 사용 가능한 IATA·ICAO 코드와 영문 별칭을 더하지만 원시 QID·날짜 응답은 브라우저에 넣지 않습니다.

현재 운항사와 신뢰할 수 있는 해산 연도가 2000년 이상인 운항사를 포함합니다. 모든 비폐기 해산 문장이 연도 이상의 정밀도로 2000년 이전임을 가리킬 때만 제외하며, 누락·거친 정밀도·상충 데이터는 보수적으로 포함합니다. 따라서 upstream의 역사 정보가 완전하다고 주장하지 않습니다. 사용자는 결과를 고르지 않고 자유 텍스트 항공사 이름을 그대로 저장할 수도 있습니다. 입력 중 Wikidata나 항공사 API를 호출하지 않습니다.

수동 갱신:

```bash
npm run update-airports
npm run update-airlines
npm run lint
npm run test
npm run typecheck
npm run build
```

`.github/workflows/update-airports.yml`은 매월 1일 좌표·검색·시간대 인덱스를 함께 검증합니다. `.github/workflows/update-airlines.yml`은 별도 시간과 자동화 브랜치에서 항공사 인덱스만 갱신하므로 어느 한 updater의 실패가 다른 updater를 막지 않습니다. 관련 생성 파일이 달라질 때만 검토 가능한 PR을 열며 `main`에 직접 쓰지 않습니다. 두 유지보수 작업 모두 현재 페이지의 개인 비행 기록에 접근하지 않습니다.

## 로컬 개발

Node.js 22 이상을 권장합니다.

```bash
npm ci
npm run dev
```

최종 검증:

```bash
npm run lint
npm run test
npm run typecheck
npm run build
npm run preview
```

개발 서버와 미리보기 서버는 기본적으로 `127.0.0.1`에만 바인딩됩니다.

## GitHub Pages 호환성

애플리케이션은 정적 Vite 빌드이며 서버 런타임이 필요 없습니다. `.github/workflows/deploy.yml`은 `main` 변경 시 `npm ci → lint → test → typecheck → build`를 실행하고 `dist`만 GitHub Pages 아티팩트로 올리도록 준비되어 있습니다. 프로젝트 저장소와 `<username>.github.io` 저장소의 base 경로를 GitHub Actions 환경에서 자동으로 구분합니다.

이 로컬 Manual V1 작업에서는 원격 생성·변경, GitHub 인증, 커밋, 푸시, 배포를 수행하지 않습니다.
